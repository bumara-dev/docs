**Date:** 2026-06-08
**Status:** Approved
**Owner:** Invoicing domain

## Summary

Register each customer with ZRA via `POST /branches/saveBrancheCustomers` automatically when the customer is created or updated in our system. The integration is best-effort: customer creation/update never fails because of a ZRA outage, and orgs without a registered VSDC device silently skip the sync. Sync status, timestamp, and last error are persisted on the customer row so the UI and admins can see and retry.

## Motivation

The existing ZRA Smart Invoice integration sends sales transmissions per-invoice, but customers themselves are never registered with ZRA. ZRA's branch-customer endpoint (`/branches/saveBrancheCustomers`) is an upsert keyed on `(tpin, custNo)`; we should call it the moment we know a customer exists so subsequent sales transmissions resolve the customer correctly on ZRA's side.

## Scope

**In scope:**
- Trigger ZRA registration after `createCustomer` and `updateCustomer` succeed.
- Track sync status, last attempt time, last error message, and last successful sync time on the customer row.
- Manual retry endpoint `POST /invoicing/customers/{customerId}/sync-zra` so the UI can offer a "Retry" action on failed customers.

**Out of scope:**
- Bulk backfill of existing customers (a one-time `for c in customers; await syncCustomerToZra(c)` script is the trivial follow-up if needed; not required as part of this plan).
- Filter on the customer list endpoint by ZRA sync status.
- Background retry of failed customers (the manual endpoint covers this).

## Approach

**Trigger:** Fire-and-forget from the HTTP handlers via `c.executionCtx.waitUntil(...)`. The DB write happens first; the ZRA call runs after the response is sent.

**Failure model:** The sync service never throws. All outcomes (success, failure, skipped) are stored on the customer row.

**No-device behavior:** Soft skip with status `skipped_no_device`. Many orgs may use invoicing without registering a VSDC device.

**Upsert semantics:** ZRA's endpoint is keyed on `(tpin, custNo)`. Same call serves both initial create and subsequent updates.

## Database schema

Add four columns to the existing `customers` table:

| Column | Type | Notes |
|---|---|---|
| `zra_sync_status` | text NULL | `'synced'` \| `'failed'` \| `'skipped_no_device'`. Null = never attempted. |
| `zra_synced_at` | timestamp NULL | Set on successful registration; preserved across subsequent failures. |
| `zra_sync_attempted_at` | timestamp NULL | Set on every attempt (success, failure, or skip). |
| `zra_sync_error` | text NULL | Last error message; cleared to NULL on success. |

No new indexes required — these columns are not query targets for normal flows. Future filter-by-status work would add `INDEX (organization_id, zra_sync_status)` then.

Migration generated via `drizzle-kit generate`. No data backfill — existing customers start with all four nulls.

## Field mapping

| ZRA field | Source | Fallback |
|---|---|---|
| `tpin` | `device.tpin` | required (skip if device missing) |
| `bhfId` | `device.branchId` | `"000"` |
| `custNo` | `customer.customerNumber` | required (always present — generated by `getNextDocumentNumber`) |
| `custTpin` | `customer.tpin` | `""` (walk-in customer) |
| `custNm` | `customer.companyName ?? customer.name` | `customer.name` is notNull |
| `adrs` | `customer.billingAddress` | `null` |
| `telNo` | `customer.phone` | `null` |
| `email` | `customer.email` | `null` |
| `faxNo` | — | `null` (we don't store fax) |
| `useYn` | `customer.isActive ? "Y" : "N"` | required boolean column |
| `remark` | — | `null` |
| `regrNm` / `regrId` | `ctx.userId ?? "SYSTEM"` | matches existing ZRA payload convention |
| `modrNm` / `modrId` | `ctx.userId ?? "SYSTEM"` | matches existing ZRA payload convention |

## Service

New file `packages/api-services/src/domains/invoicing/zra/zra-customer-sync.service.ts`:

```typescript
export async function syncCustomerToZra(
  ctx: ServiceContext,
  deps: ServiceDependencies,
  customerId: string
): Promise<{
  status: 'synced' | 'failed' | 'skipped_no_device';
  error?: string;
}>
```

**Flow:**
1. `requireOrganizationContext(ctx)` → `orgId`.
2. Load customer (`findCustomerById(db, customerId, orgId)`); if not found throw `NOT_FOUND` (this is a programmer error, not a sync failure).
3. `findVsdcDevice(db, orgId)` — existing repo function for the org's active+initialized device.
4. If no device → call `updateCustomerZraSyncStatus(db, customerId, orgId, { zraSyncStatus: 'skipped_no_device', zraSyncAttemptedAt: now })`. Return `{ status: 'skipped_no_device' }`.
5. Build `ZraBranchCustomerPayload` from `customer` + `device` (mapping above).
6. Build `ZraApiClient` from device. Duplicate the small 5-line constructor inline (same pattern as `buildApiClient` in `zra-smart-invoice.service.ts` line 54) — do not extract to a shared helper; the two services should depend on the client, not on each other.
7. Call `client.saveBranchCustomer(payload)`.
8. On `success === true` → `updateCustomerZraSyncStatus(db, customerId, orgId, { zraSyncStatus: 'synced', zraSyncedAt: now, zraSyncAttemptedAt: now, zraSyncError: null })`. Return `{ status: 'synced' }`.
9. On `success === false` → `updateCustomerZraSyncStatus(db, customerId, orgId, { zraSyncStatus: 'failed', zraSyncAttemptedAt: now, zraSyncError: result.error ?? result.message })`. Return `{ status: 'failed', error: ... }`.

**Invariant:** This function never throws (except for the `NOT_FOUND` programmer error at step 2). All operational failures result in a recorded `failed` status.

```typescript
updateCustomerZraSyncStatus(
  db: DatabaseClient,
  customerId: string,
  organizationId: string,
  patch: {
    zraSyncStatus?: 'synced' | 'failed' | 'skipped_no_device';
    zraSyncedAt?: Date | null;
    zraSyncAttemptedAt?: Date;
    zraSyncError?: string | null;
  }

```

Bypasses the regular `updateCustomer` service (which has TPIN-uniqueness validation we don't want firing on a status-only update).

## Handler integration

In `apps/api-invoicing/src/routes/invoicing/customers/handlers.ts`, both `createCustomerHandler` and `updateCustomerHandler` get an identical fire-and-forget block after their service call returns:

```typescript
const customer = await createCustomer(ctx, deps, body); // or updateCustomer

const execCtx = (c as { executionCtx?: { waitUntil: (p: Promise<unknown>) => void } }).executionCtx;
if (execCtx?.waitUntil) {
  execCtx.waitUntil(
    syncCustomerToZra(ctx, deps, customer.id).catch((err) =>
      console.error("[ZRA Customer Sync] error", { customerId: customer.id, err })
    )
  );
}

return c.json({ success: true, data: customer, message: "..." }, ...);
```

The `if (execCtx?.waitUntil)` guard means tests and non-Workers environments (where `executionCtx` is undefined) cleanly skip the sync. In production Cloudflare Workers `executionCtx` is always present.

## Manual sync endpoint

New route `POST /invoicing/customers/{customerId}/sync-zra` in `apps/api-invoicing/src/routes/invoicing/customers/`:
- Middleware: `[requireAuth, requireOrg]`.
- Awaits `syncCustomerToZra(ctx, deps, customerId)` directly — returns the status synchronously so the UI can display it.
- Responses: 200 with `{ status, error? }`, 404 if customer not found.

## Error handling

| Scenario | Behavior |
|---|---|
| Org has no active+initialized VSDC device | Status `skipped_no_device`, no API call. Customer create/update succeeds normally. |
| ZRA returns `resultCd !== "000"` | Status `failed`, error message persisted. Customer create/update succeeded; client got 201/200. |
| Network/timeout (after `makeRequest` retries) | Same as above — `ZraApiClient` returns `success: false` rather than throwing. |
| DB write inside sync throws | Caught at the handler level by the `.catch` on the `waitUntil` promise; `console.error` only. Customer row's sync status fields remain stale. Manual retry will reset. |
| Customer not found in org | `NOT_FOUND` ServiceError. Only possible if `customerId` is wrong — should not happen in the post-create path. |

**Invariant:** No code path causes the HTTP customer create/update response to fail because of a ZRA issue.

## Testing

Service unit tests at `packages/api-services/src/domains/invoicing/zra/__tests__/zra-customer-sync.service.test.ts` with mocked repo + `ZraApiClient`:
- No device → status `skipped_no_device`, no API call, customer row patched.
- ZRA success → status `synced`, `zraSyncedAt` set, error cleared.
- ZRA failure → status `failed`, error persisted, never throws.
- Field mapping: a customer with company name, TPIN, and address → expected payload (verifies `custNm` fallback, `custTpin` populated).
- Field mapping: walk-in customer (no TPIN, no company name) → `custTpin=""`, `custNm=customer.name`.
- Inactive customer → `useYn="N"`.

No HTTP-handler tests; the `waitUntil` pattern is straightforward and mirrors `triggerSyncHandler` in the reference-data feature.

## Observability

- `customers.zra_sync_status` + `zra_sync_attempted_at` + `zra_sync_error` are the primary debugging surface (visible in any customer query).
- `console.error` with `[ZRA Customer Sync]` prefix for CF Logpush filtering.
